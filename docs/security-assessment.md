# Security and resilience assessment — in progress

**Scope:** Review of the Rust CLI and its Linux synthetic acceptance fixtures through the 2026-11-02 development checkpoint. This is a concrete engineering audit log, **not** an independent security audit, a certification, or permission to import live credentials. M7-03 remains unverified until the remaining risks are assessed and tested.

## Verified controls and their evidence

| Control | Implementation or evidence | Residual limitation |
| --- | --- | --- |
| Detect changes to original exports | Source paths are compared against destinations; the shared `src/source_io.rs` reader rejects symlinks, checks descriptor/path device and inode, size, modification and change timestamps before/after bounded reads, and verifies byte count. Synthetic tests simulate in-place growth and pathname replacement; originals remain untouched. | These checks detect common races, **not** an atomic snapshot against hostile same-user writers or modifications that evade metadata checks. Use a private, quiescent copy. |
| Refuse accidental overwrites | Existing outputs fail by default; new outputs use private temporary files and hard-link no-clobber installation. When a late error follows a successful hard link, cleanup checks the staged file's device/inode before removing the newly linked output; a synthetic post-publication failure regression passes. | This does not make multiple files a crash-atomic transaction; kill/power loss and a hostile directory writer still require inspection. |
| Explicit force-replacement recovery | Replacement creates a private backup and uses rename; the opened backup source and pre-replacement pathname are compared against the original device/inode, with synthetic interruption and substitution tests | These additional checks narrow—but cannot eliminate—a hostile directory-writer race between the final check and rename; operate in a private directory |
| Companion-output rollback on normal failures | `src/bundle.rs` writes companion files **before** primary JSON and on failed writes or failed post-write identity checks removes earlier verified companions only when their device/inode still matches. Replacement/disappearance tests and the new writer's late-error cleanup test passed strict CI. | A crash, kill, changed pathname, forced replacement with uncertain durability, or a failure to remove a secret-bearing file can still leave an incomplete set. Inspect every destination after ambiguous termination. |
| Redacted reports | Synthetic canary tests confirm usernames, domains, passwords and TOTP seeds do not appear in report data | A local file path in stderr or shell history can still reveal contextual information |
| Correct secret matching | Password and TOTP values require exact equality, including capitalization; unsafe legacy `--keep` modes fail closed | Source CSVs may omit passkeys, external authenticators or other attributes |
| Authenticated conflict replay | HMAC-SHA256 over ordered full input records and matching policy, with private 32-byte key and constant-time verification | HMAC binds the source snapshot, **not** who edited review instructions |
| Private review file safety | Review keys and manifests require regular files, strict permissions, bounded sizes and matching pre-open/post-open inode identity | A same-user malicious editor or mutable source file can still modify content; use a private directory, don't share local manifests |
| Browser provenance integrity | Passflick's browser labels are bound to actual original CSV source positions, not merely user-controlled `migration.*` fields in existing Bitwarden JSON | Vaultwarden-only accounts intentionally cannot enter browser-attributed Passflick snapshots |
| Input and format bounds | Individual source inputs are capped at 64 MiB, the combined JSON/CSV batch at 256 MiB, browser source count at 32; review manifests, Passflick CSV, item counts and static Vaultwarden format sizes are also bounded | Parsing large nested metadata may still use substantially more memory than file size |
| Tracked-file privacy | `ci/release-privacy.sh` fails when source control tracks common credential-export, database, private-key, archive or backup file extensions | Filename checks **do not scan Git history or detect secret-like literals embedded in source text** |
| Isolated consumer acceptance | Real Vaultwarden import/export, duplicate-import detection, reversible Trash rollback and real Passflick CLI browser-snapshot import using synthetic disposable vaults | Not a real target-host deployment or proof that all future client/server versions behave identically |

## Open security work

1. **Multi-output failure semantics:** earlier verified companions are removed on ordinary subsequent failures only when their inode identities match. A newly hard-linked output is likewise removed on a late write/sync failure only if it still points to the staged inode. Synthetic replaced/vanished companion tests, late hard-link failure cleanup, and forced-replacement backup retention passed [strict CI run 41489697965](https://github.com/sguzman/bw-password-dedup/actions/runs/41489697965). **Independent pathnames remain nontransactional.** A power loss, process kill, failed cleanup, or uncertain forced rename can leave incomplete output; never import or retry without inspecting every expected destination and the backup. Consider a completion receipt if future operational acceptance requires a stronger bundle validity signal.
2. **Untrusted directories and filesystem races:** the JSON/CSV readers and private review reader verify opened-file identity against the initial pathname; forced-output replacement now checks the opened backup source and final pathname's inode. These protect against many substitution mistakes but cannot make an untrusted writable directory safe from concurrent pathname changes. Do not use an output folder writable by another account/process. The shared input reader now rechecks descriptor/path identity and size, mtime and ctime after reading, rejecting ordinary mid-read changes. A deliberately hostile same-user writer can still race the checks; these are not an atomic snapshot or a substitute for private, quiescent input copies. The `--force` check-before-rename window remains open.
3. **Memory and crash handling:** credentials are necessarily materialized as Rust `serde_json::Value` and temporary serialized buffers. No claim is made that secrets are zeroized from all allocations, kernel swap, core dumps, shell history, or backup/sync copies.
4. **Untrusted files and resource exhaustion:** each file is limited to 64 MiB and combined source files to 256 MiB; at most 32 browser CSV inputs are accepted. A sparse-file regression verifies the cumulative cap before parsing. Very deeply nested metadata or copies created during conservative reconciliation can still multiply resident memory beyond input size, so no strict process-memory ceiling is claimed.
5. **Licensing and distribution:** no approved project license or source release authorization has been recorded. External Passflick, the MIT test helper and GPL Bitwarden CLI are test-time tools and must not be silently bundled into a public binary.
6. **Host acceptance:** the exact EndeavourOS/fish target-host smoke test and restoration from an existing local Vaultwarden backup have not been executed. No real credentials should be processed until owner acceptance.
